# 评测服务设计（参考解与指标原语）

> 本文件是「方法」阶段四个子项目中的第一个（A）。后续：B 两个基线、C RL、D 实验与报告。
> 依据 `EXPERIMENT_PLAN.md` §7（参考解与指标）、§6（`V/U` 检查点选择）、§8（E0）、§10（产物）。
>
> **引用约定：** 本文内部的节引用写作 `§N`；对 `EXPERIMENT_PLAN.md` 的引用一律写作 `计划 §N`。

## 1. 目标与范围

本子项目交付**评测服务**：一个精确参考求解器，以及一组单实例指标原语。

**在范围内：**

- 精确最优值 `V*` 与其**被选物品集合**（可用于审计与自校验）
- 分数背包上界 `U`
- 单实例指标原语：可行性校验、精确间隙、基于上界的间隙、归一化质量 `V/U`
- 产物 `reference_results.csv`（仓库根目录，入库）

**不在范围内：**

- 跨实例聚合、表格、图、1000 次配对 bootstrap —— 属于子项目 D
- 三个方法本身（Random / Greedy 属 B，RL 属 C）

**为什么参考解不属于 `experiment/methods/`：** `EXPERIMENT_PLAN.md` §7 明确写了「This is an evaluation service, not a fourth competing method」。把它和三个参赛方法放进同一个包，正是计划 §7 想避免的混淆。

## 2. 求解器选型：一律用整数 DP，不引入 OR-Tools

计划 §7 的原文是「小规模用整数 DP，一般情形用 OR-Tools CP-SAT（10 秒超时、单 worker、固定种子）」。**实测推翻了「一般情形」这个前提。**

在冻结语料（17,700 个实例）上测得：

| 事实 | 实测值 |
| --- | --- |
| 容量上界 | `max C = 41,328`（n=200）；E3 的 n=500 为 21,201 |
| 单实例最坏规模 | `n*C = 10,600,500` 格 |
| 全语料精确求解总耗时 | **13.5 秒**（`solve()` 全程，本机；其中分数上界 2.0 秒） |
| `U ≥ V*` 违例 | **0 / 17700** |
| 平凡零最优实例（`V*=0`） | **0 / 17700** |

> **耗时那一行改过一次。** 设计初稿写的是 5.2 秒，那个数字取自更早的探针，测量范围**不涵盖** §6 的重建与自校验。按 `solve()` 的全程重测得到 13.5 秒，四项语料不变量（17700 行、`U ≥ V*` 0 违例、平凡解 0、容量上界）全部复现。
>
> 数字变了，**决定不变**：CP-SAT 每实例有 10 秒超时，17,700 个实例下界就是 49 小时；DP 的十几秒仍然胜出几个数量级。之所以还是改，是因为这张表的表头写的是「实测值」——一个未经复核就留在文档里的数字，正是本项目反复出现的那一类问题（[[tests-that-cannot-fail]]）在文档层面的翻版：**看起来像测量，实际不可复现**。

容量最大只有四万量级，**所有情形都落在「可处理容量」内**。因此 CP-SAT 分支永远不触发，而它要付出的代价是实打实的：

- 约 100 MB 的新依赖，且 `requirements.txt` 已被 `generator_fingerprint` 哈希（该指纹在 HEAD 上已不可复现，见 Plan 3 的 F4，再加重依赖只会让审计更糊）；
- 跨版本非确定性；
- 每实例 10 秒超时，以及随之而来的一整套「求解器可能没认证最优」的处理。

**用 DP 这些全部消失。** DP 是精确的、整数运算的、确定性的，每个实例都给出认证最优值，认证率恒为 100%。计划 §7 为此写的 `L`/`U` 双轨制、认证率、bound-based gap 在实现中成为死代码（见 §10 的修订说明）。

`U` **仍然保留**：计划 §6 用 `V/U` 做检查点选择，`U` 是承重的，不是为超时兜底的。

## 4. 参考解：整数 DP

```python
def solve(instance: dict) -> ReferenceSolution: ...
```

`ReferenceSolution` 的字段：

| 字段 | 含义 |
| --- | --- |
| `value` | 认证最优值 `V*`（整数） |
| `upper_bound` | 分数背包上界 `U`（`Fraction`，精确） |
| `selected_mask` | `list[bool]`，长度为 `n`，按物品的**原存储顺序** |
| `selected_indices` | 由 `selected_mask` 导出，便于调用方 |
| `certified` | 恒为 `True`（DP 是精确算法）；保留此字段以符合计划 §10 的列定义 |
| `item_set_hash` | 被选集合的规范哈希，用于审计 |
| `runtime_s` | 该实例的求解耗时（浮点） |

DP 形式：`dp[c]` = **恰好**用掉容量 `c` 时的最优价值，不可达状态置哨兵；最终答案取 `dp.max()` 而非 `dp[capacity]`。

> **这条不是形式主义。** 本设计的第一个探针脚本正是取了 `dp[capacity]`，返回了哨兵值 `-2.3e18`，而它自带的「`V* ≤ sum(values)`」校验**没能发现**——该断言对负数恒真。教训与 Plan 3 反复出现的那一类相同：*先证明检查有判别力，再相信它的沉默*。

容量轴用 numpy 向量化：对每个物品 `np.maximum(dp[w:], dp[:C+1-w] + v, out=dp[w:])`。

**dtype 与哨兵：** 工作数组与重建表统一用 `int32`，哨兵取 `-2**29`。价值总和上界为 `max sum(values) = 17,232,254`，远在 int32 内；哨兵加一个 `v` 约 `-5.19e8`，也不会溢出。统一 dtype 是为了让重建表的内存开销可控（§6）。

**这条数值界由 `_dp_table` 在每次求解时实际校验，且阈值是 `2**29 = |哨兵|`，不是 int32 的位宽。**

上面那句论证的是**不溢出**，但真正要守住的是**不可达格保持为负**——两者不是同一件事，后者的界更紧。DP 里不可达的格子拿到的是 `哨兵 + 沿路径的价值`：价值总和恰为 `2**29` 时 `哨兵 + v` 恰好是 **0**，与「空集价值 0」无法区分；再大一点就是**正数**，`dp.max()` 可能返回一个来自不可行路径的幻影最优值。一条路径至多把每件物品加一次，故能累加的上限就是所有正价值之和，于是「保持为负」的充要条件正是 `价值总和 < 2**29`。

因此把界写成断言而不是注释：换一批价值更大的实例时会**当场报错**，而不是给出一个静默错误的最优值。

**`item_set_hash` 的定义：** 对被选中的物品**索引**升序拼接后做 blake2b，形如 `blake2b("|".join(str(i) for i in sorted(selected_indices)))`，取十六进制摘要。它只覆盖**选择结果**，不覆盖值——这样「值对但集合错」的缺陷不会被哈希掩盖。取 `generate.hashing` 的同一算法族，但**不复用 `canonical_hash`**：后者是对 `(n, capacity, weights, values)` 的实例身份哈希，语义不同，混用会让审计时无法区分「实例变了」与「解变了」。

## 5. 精确上界 `U`

按 `v_i / w_i` 降序贪心，装得下就整件装入，第一个装不下的按剩余容量取分数。

**关键细节：分数项用 `fractions.Fraction` 精确计算，不用浮点。**

理由是承重的：计划 §6 用 `V/U` 作为验证分数来选择检查点。若 `U` 因浮点舍入而略小于 `V*`，则 `V/U > 1` —— 一个静默的错值，而且它会改变检查点选择的结果。用 `Fraction` 后 `U ≥ V*` 是**定理**而非容差问题，`V/U ≤ 1` 由构造保证。

`U` 在写入 CSV 时转为十进制字符串，**向上取整到 6 位小数**。向上取整是为了让*存储后的*值仍然是一个合法上界（向下取整会破坏这个性质）。

> **该取整只在 `U >= 0` 时才是「向上取整」。** 实测 `format_upper_bound(Fraction(-1,3))` 返回 `-1.666667`——既不是向上取整也不是向下取整，而是一个**静默的错值**（`-1/3` 的六位小数上界应是 `-0.333333`）。
>
> 本项目中 `U >= 0` 由构造保证：权重非负 ⇒ `remaining >= 0`；价值非负（数据模型的 `value_pence >= 0`）⇒ 每个加数非负。因此这是**已记录的前置条件**，而不是一个需要守卫的运行时状态——为一个构造上不可能出现的状态写断言，只会增加噪声。前置条件写进 `format_upper_bound` 的 docstring，让调用方看到它。

**排序必须用精确整数叉乘，不能用浮点除法。**

贪心分数解只在**按真实比值降序**时才是分数背包的最优解，也才因此是 `V*` 的合法上界。若按 `v/w` 的浮点值排序，两个不同的有理比值可能舍入到同一个 double，比较结果就不再反映真实次序；此时贪心可能给出**小于**真实分数最优的 `U`，进而可能 `U < V*`——上界性质被破坏，而计划 §6 的 `V/U` 随之失真。

`v` 与 `w` 都是整数，故比较用叉乘：`v1 * w2 > v2 * w1`，精确且廉价。次级键依次取更小的 `w`、再取原索引升序，使完整排序确定，`U` 不依赖 `sort` 的稳定性。

## 6. 重建与自校验

DP 只给出值；要得到被选集合，需要从一张 `n × (C+1)` 的表回推。

- 表用 `int32`（价值上界 `max sum(values) = 17,232,254`，远在 int32 内），最坏情形 `500 × 21202 × 4 B ≈ 42 MB`，**逐实例分配并释放**，峰值即单实例峰值。
- 若将来内存吃紧，升级路径是 Hirschberg 分治重建（`O(C)` 空间）。**现在不做**——42 MB 不是问题，为一个不存在的问题写分治重建是过度设计。

**自校验是强制的，失败即抛错、不写 CSV 行：**

1. 重建出的集合**可行**：`Σw ≤ capacity`，且每个物品至多选一次；
2. 该集合的**价值恰好等于 `V*`**。

第 2 条是 `n` 较大时唯一可用的强校验：`n≤15` 有全枚举对照（E0），`n=500` 没有。它同时把重建代码本身钉住——一个只验证「值等于 V*」的检查会漏掉重建错误，而这两条一起则要求重建结果**既可行又达到最优值**。

## 7. 指标原语

```python
def feasibility_violations(instance, selected_indices) -> int
def exact_gap(value, optimum) -> float          # 100*(V*-V)/V*
def bound_gap(value, upper_bound) -> float      # 100*(U-V)/U
def normalized_quality(value, upper_bound) -> float   # V/U，供计划 §6 检查点选择
def is_trivial_zero(instance) -> bool
```

约定：

- 所有间隙函数在分母为 0 时抛错而非返回 `inf`/`nan` —— 调用方必须先按计划 §8 剔除平凡解。**静默的 `nan` 会一路污染到汇总表**。
- `feasibility_violations` 返回**违例条数**（0 表示合法），不返回布尔值，这样「选了不存在的物品」「重复选择」「超容量」可以分别计数。
- 间隙用 `100*(...)` 的百分比口径，与计划 §7 的表格一致。

## 8. 平凡解处理

若没有任何物品装得下，所有方法必须返回空解：标记为平凡、验证可行性、**从百分比分母中剔除**、并单独报告其频次（计划 §7）。

**本语料上该分支永不触发（实测 0 / 17700）。** 因此：

- 任何形如「语料中没有平凡解」的断言都是**空转的**，它无法失败；
- 该分支必须由**合成单元测试**覆盖：手工构造一个最小重量大于容量的实例，断言 `is_trivial_zero` 为真、`solve` 返回 `V*=0` 且集合为空、且间隙函数在分母为 0 时抛错。

这条要写进设计文档而不是留给实现者发现，因为它是本项目的主导缺陷模式（[[tests-that-cannot-fail]]）在数据层面的翻版。

## 9. 产物：`reference_results.csv`

列：

| 列 | 说明 |
| --- | --- |
| `instance_id` | 与语料的 `instance_id` 一致，D 用它 join |
| `certified` | 恒为 `true`（见 §4）；保留以符合计划 §10 的「certified status」 |

| `upper_bound` | `U`，十进制字符串，向上取整到 6 位小数 |

| `solver_time_s` | 该实例求解耗时 |

**`reference_results.csv` 不是逐字节可复现的**，因为 `solver_time_s` 是墙钟测量。这与 `data_manifest.json` 的 `generated_at` 同类：**价值列是稳定的，时间列不是**。

这一点必须显式记录，且对测试有直接约束：**任何把整份 CSV 一起哈希的校验都会重蹈 Plan 3 的覆辙**（当时一个存活探针把含临时路径与时钟的 manifest 一起哈希，导致两次纯净运行都不一致，每一个「存活」判定都是假的）。比对时必须排除 `solver_time_s`。

行序：按 `instance_id` 升序，确定且与语料的文件顺序无关。

## 11. E0：正确性实验

计划 §8 定义 E0 为「三物品例子 + 100 个 `n≤15` 实例，用全子集枚举作参考」。

**实例来源：复用冻结的 `experiment.data.generate.corpus.build_instance`。** 它的 `n` 是自由参数、无最小尺寸约束；冻结语料的 `SIZES = (20, 50, 100, 200)` 不包含 `n≤15`，但直接以 `n=15` 等值调用即可，取一个专用 split 名 `e0` 得到确定性种子。这样既不新写生成器，也不改动 `generate/*`（该目录为冻结文件）。

三物品例子手工构造，使其最优解唯一（避免用「值相等但集合不同」的例子掩盖集合错误）。

断言：

1. DP 的 `V*` == 全子集枚举的 `V*`；
2. DP 重建出的集合价值 == 枚举出的最优集合价值；
3. 枚举在 `n=15` 时是 `2^15 = 32768` 个子集，规模可控。

## 12. 测试与验收

| 测试 | 内容 | 它挡住的缺陷 |
| --- | --- | --- |
| E0 | 三物品 + 100 个 `n≤15` 实例，全枚举对照 | DP 的值错、重建错 |
| 上界性质 | `U ≥ V*`，在全语料上成立 | 上界算成下界、`Fraction` 误用、排序不确定 |
| 重建自校验 | 集合可行 + 价值等于 `V*` | 重建索引错、物品重复/遗漏 |
| 金样本 | `tests/golden/reference_solutions.json`，内联 5 个小实例（`weights`/`values`/`capacity`）与其 `V*`、`U` | 求解器回归 |
| 平凡解 | 合成实例，分支行为 | 语料从不触发的分支 |
| 上界存储 | 向上取整后仍 `≥ V*` | 取整方向写反 |
| **精确排序** | 构造一对 `v/w` 浮点相等但有理数不等的物品，断言 `U` 等于精确分数最优 | **用浮点除法排序导致 `U < V*`**（§5） |
| 排序确定性（`U`） | 打乱**物品顺序**后 `U` 逐位不变 | 依赖 `sort` 稳定性、依赖 dict/set 顺序 |
| 哈希与列表顺序无关 | `item_set_hash([3,1,2]) == item_set_hash([1,2,3])` | 哈希里用了未排序的索引序列 |

> **为什么分成两行。** 初稿写的是「打乱输入顺序，`U` 与 `item_set_hash` 均不变」，这一条**按字面无法通过**：打乱物品顺序会把最优解映射成**另一组索引**，`item_set_hash` 因此本就应该变（除非最优解恰好对称）。真正与顺序无关的是两件不同的事——`U` 对**物品排列**不变（它是物品多重集的函数），`item_set_hash` 对**传入索引列表的次序**不变（它内部先排序）。分开写才能各测各的。
>
> 顺带把「打乱后仍取到同一个最优值」也测上：`U` 不变、值不变，但被选**索引**允许不同（并列最优时）。断言「集合相同」会假失败。

金样本里的 `U` 以**十进制字符串**存储（JSON 无 `Fraction` 类型），采用与 CSV 相同的向上取整口径，使金样本与产物可比。

金样本**自包含**（内联实例数据），因此不依赖 gitignore 的语料——这与冻结语料金样本的处境不同，是刻意为之：参考解的正确性不应该只有在拿到 522,504 行语料时才可验证。

## 13. 刻意不做

- **不引入 OR-Tools / CP-SAT**（§2）。
- **不做 Hirschberg 分治重建**（§6）。
- **不做跨实例聚合、表格、bootstrap** —— 属 D。
- **不修改 `experiment/data/generate/*`** —— 冻结目录，只读复用。
- **不把参考解放进 `experiment/methods/`** —— 计划 §7 的定性。
- **`reference_results.csv` 不追求逐字节可复现** —— `solver_time_s` 是墙钟测量，与 `generated_at` 同类。价值列稳定，时间列不稳定，这一点在文档里写明而不是假装它稳定。
